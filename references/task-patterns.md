# 自然语言任务到专业解读的样例

下面均为脱敏教学情景，用来选择术语和检验报告边界，不是用户项目成果。只读取与当前任务相似的部分。

## 1. “保存成功了还一直转圈，改一下”

先定位转圈在等待什么。若实际改动是收到本次写入确认即反馈成功、历史列表异步刷新，则可解释为关键写入链路与后台同步解耦，以及交互反馈时机调整。后台刷新失败仍需可见和可重试；不能提前提示一个尚未保存的任务成功。

工程师面试：说明写入回执、返回对象、旧响应覆盖风险及如何验证。产品面试：说明用户任务完成标准、反馈时机和失败恢复。只有组件测试时不能声称真实耗时下降；需要端到端同条件采样。

理解检查：如果提交超时但服务器可能已保存，直接重试会带来什么？根据实际实现讨论请求幂等或先回查，不假称已加 requestId。

## 2. “审批完了还要有人确认归档”

领域：企业流程管理。可映射为状态机、职责分离、业务终态与审计留痕。明确审批通过和实际归档是不同事件；谁有权确认、附件是否必填、历史/在途如何处理分别说明。仅要求一个确认按钮时，不自动增加全套审批平台。

面试提纲：原终态遗漏哪项业务事实 → 本次状态与责任约束 → 原有数据兼容 → 实现/验收 → 待观察的归档周期与闭环。

如果用户只要求该规则、助手设计了状态机，贡献分别写清；不能称用户做过多轮业务调研。暂无正式发布记录时说本地验证，而非“已覆盖全公司”。

## 3. “按人数、忌口、预算配一桌菜”

看实际实现：过滤和打分是多约束编排/规则驱动辅助决策；调用生成模型并有提示/上下文/输出约束时再讲生成链路。关注菜品主数据、不可放宽条件、偏好、候选不足及人工确认。

规则满足率和菜单采纳率分别测，不用“AI准确率”包办。确定性规则适合保障禁用条件；是否引入模型需说明它补哪类表达/推理能力以及错误代价。未做模型对比就写建议，不写成既往选型结论。

## 4. “问答正确率变高，帮我汇报”

读取原始记录、评分与版本口径。构造教学数据：同一小型离线集旧版12/20、新版15/20；新版16题改善/持平但有4题退化时应核对逐题转移，不能只凭总体统计猜退化类型。若没有题级数据，不创造这些比较细节。

仅12/20与15/20可算60%与75%，提高15个百分点；不能据此称生产准确率或人工成本下降。历史基线不能写成同期 A/B；规则禁止、证据不足和资料冲突需各自评估。高风险退化即使总分提升也应单列准入判断；尚未经用户评审时不把“决定不上线”记为用户决策。

## 5. “把按钮颜色和间距统一”

若仅为样式改动，讲视觉一致性、可辨识性与适用的布局检查。没有点击误差、可用性测试或行为数据，不写转化提升；不称为中台建设、架构治理或业务流程再造。对一次简单改动输出短解读即可。

## 6. “只做报告，别改程序、别发布”

仅分析有权读取的输入，输出专业解释与证据缺口，不补需求、不跑生产写操作、不替用户提交/发布。已有记录能支持哪个阶段就写哪个阶段。跨岗位版本调整的是叙述焦点，不改变事实或个人责任。

## 讲解质量自检

读者应能说出问题是什么、哪项机制解决它、为什么选择该方案、如何验证、哪些收益仍待测。如果只能背术语，则补“术语在本次改动中对应什么”和一个反例；不要只把最终话术写得更长。
