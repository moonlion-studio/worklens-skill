# 指标与证据口径

在指标命名、前后比较、AI 评测或收益解释时读取本文件。

## 别跨越证据层次

| 层次 | 可说什么 | 还不能推出什么 |
|---|---|---|
| 实现与本地验证 | 已增加规则/接口、指定场景测试符合预期 | 已发布、真实用户已使用 |
| 环境交付 | 指定后端已部署或开发包已上传，并有对应回执 | 前端已正式发布、全部端口有效 |
| 实际使用 | 某真实角色完成某业务任务，有记录/反馈 | 全部用户采纳、长期稳定、平均提升 |
| 过程效果 | 在限定样本/周期下，耗时、返工、失败等观察值变化 | 全公司降本或因果收益 |
| 业务结果 | 有口径、有样本、有时间窗的真实结果 | 不具备对照时的因果结论、未来保证 |

一笔真实成功可以证明一个闭环；没有样本覆盖就不推成稳定成功率。测试条数、处理记录数、页面数和部署检查数不是效率提升。文件时间和 Git 提交不是验收时间。

## 指标至少写清这些条件

指标名、业务对象/单位、起止事件或分子分母、纳入/排除范围、时间窗、样本量、原始来源、比较条件和局限。没有数字时，只写一个最值得采集的指标及操作办法，不生成伪精确统计。

常用选择：

- **耗时**：同任务从用户开始操作到目标完成；等待审批、网络请求与人在页面操作可分段。固定角色、设备/网络和完成标准，展示中位数/P95及样本量。没有前测，就先建立当前基线。
- **闭环率**：同批进入流程的对象，在固定观察窗口内完成全部必要节点的数量/该批符合条件对象；撤回、作废、未到期及历史遗留分开，不能用累计完成/今日新增混算。
- **自动处理率**：在明确适用范围内，无需人工补充/修改而完成目标的任务数/全部适用任务数；人工复核是否算自动必须约定。调用 AI、生成草稿、执行脚本不自动等于自动完成。
- **采纳率与人工修改率**：采纳/修改的对象粒度是整份方案、单项内容还是单次任务，先固定；强制选择或没有替代入口时不能直接视为偏好认可。
- **数据质量**：完整性、有效性、一致性、唯一性分别衡量；空值减少不能直接命名为模型准确率。
- **AI 质量**：检索 Recall@k 要有相关证据标注；回答正确率要有问题级金标准与评分；引用支持率要逐断言核对；结构合法率只评价协议；任务完成率要验证实际目标。规则满足率不叫 LLM 准确率。

## 计算与比较

- 耗时减少比例 = (基线耗时 - 新耗时) / 基线耗时；基线须大于零且统计量/样本条件可比。
- 通过率 = 通过数 / 符合统计口径的总数；部分通过如何处理要明示。
- 从 60% 到 75% 是提高 15 个百分点，相对提高 25%；两者不能混写。此数字仅为教学例子。
- 历史基线和不同时间复测不自动叫 A/B；数据、模型、检索、提示、硬件和运行模式的差异需标明。
- 总体改善可能伴随特定业务/角色退化；保留退化样本和严重错误，不能只报平均值。
- 正常业务收益、构造样本结果、离线评测、用户估计和预测目标分别标注。合成数字可用于公式教学，不能填成用户经历。

## 面试与汇报中的安全表达

已实现：建立了某约束，使某错误路径被校验拦截；依据是指定测试/实际回执。

合理预期：该改动减少了流程中的一个等待依赖，预期改善提交体验；真实端到端耗时尚待同条件采样。

无收益基线：已验证流程可用，下一阶段采集处理周期、人工介入与失败原因；不要给“提升约30%”之类没有来源的估计。

一次复核不代表用户已理解全部设计。个人能力评价需要用户能解释原因、边界和验证，或有其实际评审/操作证据。
