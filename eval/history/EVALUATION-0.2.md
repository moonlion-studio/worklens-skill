# WorkLens 测试报告

日期：2026-11-08。结论：适合以专业复盘辅助工具的预览版继续验证，暂不具备“自动输出可直接外发可信报告”的证据。真人理解与面试表现尚未测试。

## 测了什么

- 7 个构造任务：预约异步同步、规则配餐、RAG 历史评测、样式微调、403 导出失败、CSV 批次导入、信息不足的筛选需求。
- 第一轮：7 次加载原 Skill 的报告生成；预约与配餐另有 2 次不加载 Skill 的基线，共 9 份输出。
- 根据失败调整指令，再用同样 7 个场景做第二轮回归，共 7 份输出。
- 总共 16 次本机模型调用，保留原始输出。没有删掉失败结果，也没有用人工修订稿替换原始响应。所有响应正常结束，没有输出截断或接口失败。
- 原企业数据没有进入测试。用例是根据常见任务抽象的构造材料，数字也仅是测试数据。

## 环境与方法

后端为本机 Ollama `qwen2.5:7b`，temperature=0.2、seed=42、num_ctx=16384、num_predict=1800；每轮运行前加载 Skill 与两份参考文件。参数与内容 SHA-256 在各轮 metadata.json 中。

这是可复跑的小模型报告压力测试，不是 Codex 当前模型的独立端到端测试，也不代表所有模型的表现。固定加载全部参考文件与真实宿主按需读取资源的方式也有差异。

评分检查点与 prompt 分开保存，检查点没有发送给生成模型。任务作者根据原始输入逐例人工复核，并非独立专家盲评。第二轮复用首轮用例，仅验证回归，未设置独立留出集。

判断包含：机制/术语是否对应事实、取舍是否有依据、数字与状态是否一致、个人贡献是否有来源、讲解是否能用于理解和追问。关键结论不受事实错误影响才列为“基本满足”；只有部分做到列为“部分满足”；关键事实、风险或责任错误列为“需修订”。“基本满足”也不代表文案可以免审核。

## 第一轮发现

第一轮 7 份 Skill 报告均未达到可直接外发门槛。主要发现：

| 场景 | 有帮助的部分 | 未通过原因 |
|---|---|---|
| 预约同步 | 解释了保存与历史同步解耦 | 补写单元/集成测试，混淆谁实现，泛化一致性效果 |
| 规则配餐 | 没有继续把规则编排叫模型生成 | 将 28/35 在面试/汇报中写成全部方案满足 |
| RAG 评测 | 保留部分逐题变化 | 推定更换模型、误说同条件、遗漏权限退化重点 |
| 样式微调 | 范围基本贴合样式 | 无证据地推导点击区域改善和误触减少 |
| 403 导出失败 | 保留未发布及需求/实现分工 | 把响应码断言为配置根因，补写大文件性能理由 |
| CSV 导入 | 提到校验、事务和本地验证 | 虚构原系统行为，遗漏幂等与批次状态的重要性 |
| 信息不足 | 提供了完整结构 | 编造方案、测试、用户反馈和个人贡献 |

两份未加载 Skill 的基线也出现错误：预约例混淆异步与主线程阻塞，配餐例将规则测试叫作 AI 准确率并暗示不调用模型就是基础实现。这只能支持观察个别叙述差异，不能证明 Skill 的总体效果提升。

## 据此修订了什么

1. 将事实准确置于术语丰富与模板完整之前，复杂任务先列事实卡。
2. 明确报告正文、面试稿和汇报稿都要保留样本、失败/退化、环境及责任边界。
3. 限制未经支持的测试类型、根因和个人职责；基线/候选不自动表示更换模型。
4. 区分错误响应与根因，机制变化与已测收益；证据不足时允许省略栏目。

这些是指令修订，不是程序级事实保证。

## 第二轮结果

| 用例 | 判断 | 观察 |
|---|---|---|
| C01 预约同步 | 需修订 | 状态与测试名称更贴近输入，但新增重复提交现象，仍漏掉部分保护说明 |
| C02 规则配餐 | 部分满足 | 保留 28/35 与真实采纳缺口，未再说全部通过；仍未算出并正确命名 80% 规则满足率 |
| C03 RAG 评测 | 需修订 | 保留评分未独立复核及个人判断未知；仍遗漏权限退化严重性和 16 个百分点变化 |
| C04 样式微调 | 基本满足 | 范围保持样式，保留本地/未做用户测试边界，未编造转化率或架构成果；文案仍可精简 |
| C05 导出失败 | 需修订 | 一处承认 403 未生成，另一处又说接口联调通过，报告自相矛盾 |
| C06 CSV 导入 | 部分满足 | 覆盖校验、事务、唯一键和批次日志；个人贡献仍模糊，缺理解追问 |
| C07 信息不足 | 需修订 | 仍补出未提供的旧系统能力、实现和测试 |

本轮为 **1 例基本满足、2 例部分满足、4 例需修订**。这不是产品准确率或稳定性承诺。两个最明显的遗留风险是：材料不足时补写事实，以及生成不同讲法时丢失风险/证据边界。

## 能否解决痛点

有支持的结论：Skill 能组织专业复盘的结构，部分场景能将任务与概念连接，并提醒验证范围；用户可以据此准备讲解和补证。

尚无支持的结论：报告稳定准确、能免审核外发、用户能够独立应对技术追问、学习效果长期保留、面试表现或录用率提升。小模型测试还显示，明确写入规则并不保证模型遵守。

因此当前定位为需要核对的复盘与学习辅助工具，不宣传为自动背书系统。对权限、资金、业务核算、指标及个人贡献等内容，应回到原始证据核实。

## 如何继续验证

按 [真人理解验证方法](../USER_CHECK.md)，记录使用者读报告前、读后关掉报告、次日复述以及新情景追问的表现。按相同标准对照，保留原话和事实依据，才有条件评价“做了却讲不清”的痛点是否被缓解。

还需在目标宿主和更强模型上独立运行相同用例，并新增未参与修订的留出任务。不能将后续人工修订示例当作模型复测通过。
